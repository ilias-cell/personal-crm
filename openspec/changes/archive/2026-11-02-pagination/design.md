# Design

## Context

Зачем и что меняется — в `proposal.md`, поведение и сценарии — в `specs/contact-list/spec.md`.

Что есть сейчас:

- Главная — `src/app/page.tsx`. Список `ContactList` внутри `<Suspense>` читает `searchParams`, вызывает `listContacts(search)` и `countContacts()` из `src/lib/contacts.ts` и выводит все строки. У строк `content-visibility: auto` — попытка удешевить тысячу строк в браузере.
- `listContacts` строит условие поиска и порядок: при поиске — сначала совпадения с начала слова, затем `created_at desc, id desc`. `id` уникален, поэтому порядок однозначный. Для порядка без поиска есть индекс `contacts_created_at_idx (created_at desc, id desc)`.
- Поиск — клиентский `SearchInput` (`src/components/search-input.tsx`): через 200 мс после ввода делает `router.replace("/?q=...")` в `startTransition` и ставит `data-pending`; список бледнеет через `group-has-data-pending/contacts:opacity-60`.
- Включены `cacheComponents` и `partialPrefetching`: всё, что читает базу или адрес, должно быть внутри `<Suspense>`.
- «Все контакты» — `BackLink href="/"` (`src/components/back-link.tsx`) в карточке, на «Добавить контакт» и на «Пора связаться»; ещё кнопка `Link href="/"` в пустом состоянии «Пора связаться».
- После сохранения нового контакта и после удаления действия делают `redirect("/")`.
- shadcn/ui в стиле `base-nova`, кнопки — `@base-ui/react` с пропом `render`. Автотестов нет; проверка — `pnpm lint`, `pnpm typecheck`, `pnpm build` и руками.

## Goals / Non-Goals

**Goals:**

- При 998 контактах главная весит в разы меньше: HTML около 150 КБ без сжатия вместо 2,5 МБ, ответ сервера — как у карточки контакта.
- Смена страницы не перезагружает всё приложение: переход внутри приложения, как сейчас поиск.
- Без изменений в базе данных.

**Non-Goals:**

- Переход «после контакта X» (keyset) вместо номера страницы — см. решение 2.
- Возврат к той же строке внутри страницы: «Все контакты» открывает нужную страницу с её начала. Точное место прокрутки восстанавливает только кнопка «Назад» в браузере.
- Страницы на «Пора связаться».

## Decisions

### 1. Номер страницы — параметр `page` в адресе

- Адрес: `/?q=анна&page=2`. Первая страница — без `page`: `/` и `/?q=анна`. Так старые ссылки и ссылка «Показать все контакты» работают без изменений.
- Разбор — как у `parseContactId`: только `^[1-9]\d{0,5}$`, иначе 1. Ноль, минус, буквы, пустое значение, несколько `page` — первая страница (берём первое значение, как для `q`).
- `SearchInput` по-прежнему пишет в адрес только `q`, без `page` — поэтому любой новый текст поиска и очистка открывают первую страницу. Менять компонент поиска не нужно.

Альтернатива — хранить страницу в состоянии браузера без адреса: отвергнуто, спека требует ту же страницу по ссылке в другом браузере и работу кнопки «Назад».

### 2. Выборка: сначала число, потом страница через `limit`/`offset`

В `src/lib/contacts.ts`:

- Условие поиска и порядок выносятся в общую функцию, чтобы список и подсчёт фильтровали одинаково.
- `countContacts(search)` — сколько контактов подходит под поиск; без поиска — все.
- `listContacts(search, page)` — тот же запрос, что сейчас, плюс `.limit(PAGE_SIZE).offset((page - 1) * PAGE_SIZE)`.

`ContactList` сначала узнаёт числа (найденные и, если идёт поиск, всего — параллельно), считает последнюю страницу `max(1, ceil(найдено / 50))`, ограничивает запрошенную страницу последней и только потом берёт строки. Так «страница 30 из 20» показывает 20-ю без второго запроса строк.

Альтернативы:

- `count(*) over()` в том же запросе — отвергнуто: на несуществующей странице строк нет, а значит и числа нет; всё равно нужен второй запрос.
- Keyset («контакты после id X») — быстрее на очень дальних страницах, но не умеет «открыть страницу 7» по номеру и сложно сочетается с порядком по совпадению при поиске. Для тысяч контактов `offset` стоит доли миллисекунды.
- Брать всё из базы и резать в Node — отвергнуто: сервер продолжал бы читать и пересылать тысячу строк.

Один лишний запрос к базе (число до строк) — около миллисекунды в одной сети Docker; это приемлемо.

### 3. Логика страниц — отдельный модуль без React

`src/lib/pagination.ts` (без `server-only`, нужен и серверу, и браузеру):

- `PAGE_SIZE = 50`;
- `parsePage(raw)` — решение 1;
- `getPageItems(current, pageCount)` — номера и «…» по правилу спеки: первая, последняя, текущая ±1, промежуток из одной страницы заменяется её номером; всегда не больше 7 элементов. Это известное правило с `boundaryCount = 1`, `siblingCount = 1`: начало отрезка соседей `max(min(current − 1, pageCount − 4), 3)`, конец `min(max(current + 1, 5), pageCount − 2)`;
- `contactListHref({ search, page })` — адрес списка; первая страница без `page`.

Чистые функции проверяются разовым скриптом через `tsx` на примерах из спеки, без новой тестовой библиотеки.

### 4. Переключатель — компонент `pagination` из shadcn/ui

- Ставим `pnpm dlx shadcn@latest add pagination`. Он зависит только от уже установленных `button`, `cn` и `lucide-react`; новые пакеты в `package.json` не ожидаются.
- После установки в `src/components/ui/pagination.tsx`:
  - `PaginationLink` рендерит `next/link` вместо `<a>` через проп `render` у кнопки base-ui — переход внутри приложения, с предзагрузкой;
  - подписи по-русски: «Назад», «Вперёд»; для экранного диктора — «Страницы списка», «Предыдущая страница», «Следующая страница», «Страница N», «Ещё страницы»; у текущей страницы `aria-current="page"`;
  - неактивная стрелка — не ссылка, а `<span aria-disabled="true">` с теми же стилями и `opacity-50`: на неё нельзя нажать и нельзя попасть клавишей Tab.
- Обёртка `src/components/contact-list-pagination.tsx` (серверный компонент) получает `page`, `pageCount`, `search` и собирает переключатель из `getPageItems` и `contactListHref`. Рендерится дважды — над и под списком — и ничего не выводит, если страница одна.
- Размеры: на телефоне кнопки 32 px (`size-8`, как в shadcn по умолчанию), чтобы 9 элементов (7 номеров и 2 стрелки) поместились в 327 px — ширину экрана 375 px без полей `px-6`. Слова «Назад»/«Вперёд» скрыты до `sm` (в компоненте shadcn это уже так). С `sm` кнопки 36 px (`size-9`).

### 5. Раскладка

- Над списком одна строка: слева подпись, справа переключатель. На телефоне — две строки: подпись, под ней переключатель по центру.
- Под списком — только переключатель, на том же месте по горизонтали, что и верхний.
- Подписи — функции в `src/lib/format.ts` с `formatNumber` и длинным тире: «Показаны 51–100 из 998», «Найдено: 120 из 998 · показаны 51–100». Для одной страницы — прежние тексты. `aria-live="polite"` у подписи остаётся.
- `content-visibility: auto` у строк и комментарий про тысячу строк убираем: строк не больше 50.

### 6. Пока открывается другая страница

Переход по ссылке в App Router — это переход в `startTransition`, как у поиска: старая страница остаётся на экране, пока не придёт новая. Чтобы было видно, что нажатие сработало, внутри каждой ссылки переключателя маленький клиентский компонент через `useLinkStatus()` ставит пустой `<span data-pending hidden>`, пока идёт переход. Существующий `group-has-data-pending/contacts:opacity-60` делает список бледнее — так же, как при поиске.

Прокрутка: по умолчанию `next/link` после перехода прокручивает к началу изменившейся части страницы, если она не видна. При нажатии в нижнем переключателе это начало страницы — что и требует спека. Но в `globals.css` у `<html>` стоит `scroll-behavior: smooth`, и без дополнительной настройки страница целую секунду плавно едет вверх через весь список, а Next пишет об этом предупреждение в консоль. Поэтому у `<html>` атрибут `data-scroll-behavior="smooth"` — рекомендация Next: при переходе на другую страницу экран сразу встаёт на её начало, плавная прокрутка внутри страницы остаётся. Это касается всех переходов в приложении, не только списка.

### 7. «Все контакты» — место в списке хранится в `sessionStorage`

- Запись: клиентский компонент `RememberContactListHref` на главной (внутри `<Suspense>`, потому что читает `useSearchParams`) при каждом изменении адреса списка пишет `/` + строку запроса в `sessionStorage` под ключом `contact-list-href`.
- Чтение: клиентский компонент `ContactListLink` через `useSyncExternalStore`. На сервере и при первой отрисовке — `/`, после загрузки страницы в браузере — сохранённый адрес. Так нет расхождения разметки сервера и браузера. Принимаем только значения `/` и `/?…`, иначе `/`. Обращение к `sessionStorage` — в `try/catch` (в некоторых режимах приватности оно бросает ошибку), при ошибке `/`.
- `BackLink` получает вариант без `href`, который берёт адрес из `ContactListLink`; им заменяются «Все контакты» в карточке, на «Добавить контакт», на «Пора связаться» и кнопка в пустом состоянии «Пора связаться».
- Не меняются: название приложения в шапке (`/`), переход после сохранения нового контакта и после удаления (`redirect("/")`), ссылка «Показать все контакты» в пустом поиске.

Почему `sessionStorage`: он живёт в одной вкладке — ровно то, что требует спека, — и переживает перезагрузку страницы.

Альтернативы:

- Передавать место в адресе карточки (`/contacts/5?from=...`) — отвергнуто: длинные адреса, параметр пришлось бы протаскивать через редактирование, сохранение и заметки.
- `router.back()` — отвергнуто: после «Редактировать → Сохранить» вернёт в форму, а при открытии карточки по ссылке — вообще со страницы.
- Cookie — отвергнуто: общая для всех вкладок, и серверу пришлось бы читать её на каждой странице.

## Risks / Trade-offs

- [Пока открыты страницы, кто-то добавлен или удалён — контакты сдвигаются между страницами, один может повториться на следующей странице или пропустить её] → Приемлемо для личной CRM с одним владельцем; при обновлении страницы всё снова верно.
- [Сохранённый адрес «Все контакты» подставляется после загрузки скриптов; если нажать ссылку раньше, откроется первая страница] → Окно — доли секунды; ссылка всё равно ведёт в список.
- [Открытие карточки в новой вкладке через Cmd/Ctrl+клик: браузер может скопировать `sessionStorage` в новую вкладку, а может нет] → В обоих случаях «Все контакты» ведёт в список — либо на то же место, либо на первую страницу. Сценарий спеки про новое окно проверяем, открывая ссылку в отдельном окне.
- [Предзагрузка: ссылки переключателя (до 18 на странице) предзагружаются, когда видны] → С `partialPrefetching` предзагружается только общий каркас страницы, без списка из базы; нагрузка на сервер мала. Проверяем вкладкой «Сеть» в браузере.
- [Если Next покажет при переходе заглушку списка вместо бледного старого списка] → Тоже приемлемо: экран не пустой, видно, что идёт загрузка.
- [На телефоне уже 375 px переключатель может не влезть, если номера трёхзначные (больше 5 000 контактов)] → Для личной CRM нереально; на 375 px с двузначными номерами проверяем руками.

## Migration Plan

- База не меняется, миграций нет. Выкатка обычная: PR → merge в main → образ → миграции (пустой шаг) → новый образ → smoke `/health`.
- Откат — вручную на предыдущий образ, как всегда; данных новая версия не меняет, поэтому откат безопасен.
- После выкатки замерить главную на сервере тем же способом, что и до: размер HTML и время ответа.
