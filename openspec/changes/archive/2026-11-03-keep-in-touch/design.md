# Design

## Context

Зачем и что меняется — в `proposal.md`, правила отсчёта и сценарии — в `specs/keep-in-touch/spec.md`.

Что есть сейчас:

- Таблицы `contacts` и `notes` в `src/db/schema.ts`. Заметки можно только добавлять: удалить или изменить заметку нельзя. Поэтому дата последней заметки только растёт, а «есть ли у контакта заметки» не может смениться с «да» на «нет» (контакт удаляется только целиком, вместе с заметками).
- Индекс `notes_contact_created_at_idx (contact_id, created_at desc)` уже есть: последнюю заметку контакта он находит сразу.
- Формы и действия: `src/components/contact-form.tsx`, `src/app/actions.ts` (`createContact`, `updateContact`, `addNote`). Проверка полей — zod в `src/lib/validation.ts`, общие для браузера и сервера типы — `src/lib/contact-form.ts`.
- Включён `cacheComponents`: всё, что читает базу при открытии страницы, должно быть внутри `<Suspense>`.
- Часовой пояс нигде не задан. Сервер приложения в Docker работает по UTC, поэтому «сегодня» и «день заметки» нельзя брать из времени процесса Node.
- shadcn/ui в стиле `base-nova`, библиотека `@base-ui/react` уже стоит.
- Автотестов в проекте нет; проверка — `pnpm lint`, `pnpm typecheck`, `pnpm build` и руками.

## Goals / Non-Goals

**Goals:**

- Правила отсчёта из спеки хранятся в базе так, чтобы срок любого человека считался одним запросом, без истории изменений.
- Срок, фильтр и сортировка считаются в PostgreSQL, по московскому календарю.
- Старая версия приложения продолжает работать с новой схемой базы: миграция только добавляет пустые поля.

**Non-Goals:**

- История изменений частоты.
- Пагинация на странице «Пора связаться»: просроченных обычно немного, показываем всех.
- Поиск и фильтры на странице «Пора связаться».
- Часовой пояс у уже существующих дат в карточке (см. Risks).

## Decisions

### 1. Два новых поля у контакта

- `touch_frequency` — частота: перечисление PostgreSQL `touch_frequency` со значениями `week`, `month`, `quarter`, `year`; пусто — «Не задано».
- `touch_restarted_at` — момент, с которого срок начат заново (timestamptz); пусто — перезапуска не было.

День отсчёта = самое позднее из «последняя заметка» и `touch_restarted_at` (`greatest()` в PostgreSQL пропускает пустые значения). Так все правила спеки сводятся к тому, когда записывать `touch_restarted_at`:

| Что было → что стало | `touch_restarted_at` |
| --- | --- |
| Новый контакт с частотой | сейчас |
| Новый контакт без частоты | пусто |
| «Не задано» → частота, заметок нет | сейчас |
| «Не задано» → частота, заметки есть | пусто (считать от последней заметки) |
| Частота → другая частота | сейчас |
| Частота → та же частота | не меняется |
| Частота → «Не задано» | пусто |

Альтернативы:

- Хранить срок в днях (7/30/90/365) — отвергнуто: спека требует календарные месяцы (15 января → 15 февраля).
- Хранить «когда задали частоту» всегда и вычислять остальное — отвергнуто: потом не отличить «задали впервые человеку со старыми заметками» (считать от заметки) от «поменяли частоту» (считать от дня смены).
- Отдельная таблица истории — избыточно для одного правила.
- Текстовое поле вместо перечисления — перечисление не даст записать в базу опечатку.

### 2. Смена частоты — одним запросом `UPDATE`

`updateContact` записывает частоту и `touch_restarted_at` одним `UPDATE` с `CASE`, который смотрит на старое значение частоты в той же строке и на наличие заметок (`exists`). В `SET` PostgreSQL видит значения строки до изменения, поэтому таблица выше переносится в `CASE` один к одному, без отдельного чтения и без гонки двух вкладок. `createContact` записывает `touch_restarted_at = now()`, если частота выбрана.

### 3. Срок считается в PostgreSQL по московскому времени

Для каждого контакта с частотой:

- последняя заметка — `(select max(created_at) from notes where contact_id = contacts.id)`;
- день отсчёта — `(greatest(последняя_заметка, touch_restarted_at) at time zone 'Europe/Moscow')::date`;
- день срока — день отсчёта + интервал (`7 days`, `1 month`, `3 months`, `1 year`). PostgreSQL сам сдвигает 31 января + 1 месяц на 28/29 февраля;
- сегодня — `(now() at time zone 'Europe/Moscow')::date`;
- просрочка в днях — сегодня − день срока; человек на странице, если просрочка ≥ 0.

Сортировка: день срока по возрастанию, затем имя, затем `id`. Имя сравнивается правилами сортировки базы; если окажется, что «ё» или регистр сортируются не по-русски, — сравнивать по `translate(lower(name), 'ё', 'е')`, как уже сделано в поиске.

Часовой пояс — одна константа `OWNER_TIME_ZONE = "Europe/Moscow"` в коде, ею пользуются запрос и вывод дат на новой странице.

Альтернатива — считать в JavaScript: отвергнута, потому что календарные месяцы и часовой пояс без новой библиотеки считать неудобно и легко ошибиться, а фильтр и сортировку всё равно лучше делать в базе.

### 4. Где лежит код

- `src/db/schema.ts` — перечисление и два поля; миграция `drizzle/0001_*.sql` создаётся `pnpm db:generate`.
- `src/lib/contact-form.ts` — список частот и русские подписи (нужны и форме в браузере, и карточке на сервере); поле `touchFrequency` в `ContactFormValues`.
- `src/lib/validation.ts` — `touchFrequency`: пустая строка → `null`, иначе одно из четырёх значений.
- `src/lib/keep-in-touch.ts` (только сервер) — `listOverdueContacts()` и `countOverdueContacts()` на общем запросе из решения 3, плюс проверка «задана ли частота хоть кому-то» для пустой страницы.
- `src/app/keep-in-touch/page.tsx` — страница `/keep-in-touch`.
- `src/lib/format.ts` — «просрочено на N дней» с правильным склонением (как `formatNoteCount`), дата в московском времени.

### 5. Поле в форме — `native-select` из shadcn/ui

Компонент shadcn `native-select` — оформленный обычный `<select>`: сам отправляется вместе с формой, на телефоне открывает системный список, не требует JavaScript и новых пакетов. Добавляется командой `pnpm dlx shadcn@latest add native-select`.

Альтернатива — `select` (выпадающее окно на `@base-ui/react`): красивее на компьютере, но значение в форму уходит через скрытое поле, и на телефоне неудобнее. Берём его, только если `native-select` нет в реестре для `base-nova`.

Если команда `shadcn add` попытается поставить новый npm-пакет — остановиться и спросить владельца (правило «новую библиотеку — обсуждать»).

Поле стоит последним в форме, после «Почта». В карточке строка «Как часто общаться» — после «Почта», перед «Добавлен».

### 6. Ссылка в шапке главной

Ссылка «Пора связаться» отрисовывается сразу, а число просроченных подгружается внутри `<Suspense>` (запрос к базе), запасной вариант — ссылка без числа. Так шапка не ждёт запроса.

### 7. Свежесть данных после заметки и правки

`updateContact` уже вызывает `revalidatePath("/", "layout")`. `addNote` сейчас вызывает только `refresh()` — этого хватает для карточки, но при возврате на главную или на «Пора связаться» кнопкой «Назад» браузер может показать старый список. В `addNote` добавляется `revalidatePath("/", "layout")`: он сбрасывает сохранённые страницы, и счётчик со списком читаются заново. Проверяется руками: заметка → «Назад» → человек пропал.

### 8. Тестовые данные не меняем

Сид (`src/db/seed.ts`) работает только на пустой базе, а локальная и серверная базы уже наполнены — правка сида на них не подействовала бы. Для ручной проверки хватает выдуманных контактов со старыми заметками: им задаётся частота, и они сразу попадают на страницу. Новые поля сид не заполняет, частота у его контактов — «Не задано».

### 9. Внешний вид — по макетам

Макеты экранов для компьютера и телефона: https://claude.ai/artifact/PMXaTguLuWPWzdN2ArHoZV. Тексты берутся из спеки, цвета, шрифты и отступы — только из токенов `src/app/globals.css`; если макет и токены расходятся, правы токены. Сверх спеки по макетам:

- «пора сегодня» — цветом ссылок (`text-accent`); «просрочено на N дней» — основным цветом, `font-medium`.
- У ссылки «Пора связаться» в шапке главной — значок часов (`ClockIcon` из lucide-react), так же, как `PlusIcon` у «Добавить контакт».
- Строка на странице «Пора связаться». На компьютере: аватар, имя, под ним «частота · Последняя заметка: дата», просрочка справа. На телефоне — три строки без обрезки: имя, под ним просрочка, ещё ниже «частота · Последняя заметка: дата».
- Пустые состояния — как пустой список на главной: компонент `Empty` с пунктирной рамкой, значок (часы — «частота не задана никому», галочка в круге — «Со всеми на связи»), заголовок, пояснение и кнопка «Все контакты» в стиле `outline`.
- Пояснение под заголовком страницы и подсказка под полем частоты — `text-muted-foreground`, как подписи в карточке.

## Risks / Trade-offs

- [Сервер работает по UTC, а существующие даты заметок в карточке выводятся без часового пояса] → на новой странице дата последней заметки выводится по Москве, как и считается срок. Существующие даты в карточке в этой фиче не трогаем: если они на сервере правда показываются по UTC, это отдельная правка, решает владелец. Пока она не сделана, заметка, написанная между полуночью и 3:00 по Москве, в карточке может стоять предыдущим днём.
- [Смена частоты сбрасывает срок — ей можно «отложить» человека] → так решил владелец; это видно в спеке.
- [Запрос считает последнюю заметку для каждого контакта с частотой] → при тысяче контактов это доли миллисекунды благодаря существующему индексу; новый индекс не нужен.
- [Нет автотестов на правила отсчёта] → после реализации проверить правила SQL-запросом к локальной базе с подставленными датами (31 января, день срока, накануне, заметка в 23:30 по Москве) и руками по сценариям спеки.

## Migration Plan

1. Миграция `0001`: создать перечисление `touch_frequency`, добавить в `contacts` два пустых поля без значений по умолчанию. Это мгновенно и не переписывает таблицу.
2. Выкатка обычная: миграции → новый образ → smoke `/health`.
3. Старая версия приложения с новой схемой работает: Drizzle перечисляет поля явно, лишние поля игнорирует. Поэтому ручной откат на предыдущий образ возможен без отката миграции; поля останутся пустыми или с данными и не помешают.
4. Ничего у существующих контактов не меняется: частота у всех «Не задано».
