# Design

## Context

Зачем и что меняется — в `proposal.md`, поведение и сценарии — в `specs/contact-groups`, `specs/contact-list`, `specs/keep-in-touch`.

Что есть сейчас:

- Таблицы `contacts` и `notes` в `src/db/schema.ts`; миграции в `drizzle/`, последняя — `0001_keep_in_touch.sql`.
- Главная `src/app/page.tsx`: шапка, поиск (`src/components/search-input.tsx`, пишет `?q=` в адрес через `router.replace`), подпись (`formatContactListSummary` в `src/lib/format.ts`), список и переключатель страниц (`contactListHref` в `src/lib/pagination.ts`). Запросы списка — `src/lib/contacts.ts` (`searchContacts`, `listContacts`, `countContacts`).
- «Все контакты» запоминает адрес списка целиком (`RememberContactListHref` в `src/components/contact-list-link.tsx`): новый параметр адреса попадёт туда сам.
- Карточка `src/app/contacts/[id]/page.tsx` со списком сведений `DetailRow`; «Пора связаться» — `src/app/keep-in-touch/page.tsx` и `src/lib/keep-in-touch.ts`.
- Серверные действия — `src/app/actions.ts`; ошибки базы пишутся в лог без данных людей через `describeDbError` / `withoutQueryData` (`src/db/errors.ts`).
- Включён `cacheComponents`: всё, что читает базу при открытии страницы, — внутри `<Suspense>`.
- Компоненты shadcn/ui в стиле `base-nova` поверх `@base-ui/react`; `popover` и `badge` ещё не добавлены.
- Автотестов нет: нет Vitest, нет тестовой базы. CLAUDE.md требует TDD, правило OpenSpec — тест на каждый сценарий. e2e и CI владелец отложил.
- `AGENTS.md`: эта версия Next.js отличается от привычной — перед кодом читать `node_modules/next/dist/docs/`.

## Goals / Non-Goals

**Goals:**

- Группы и членство хранятся в двух таблицах; фильтр, числа и метки считаются в PostgreSQL.
- Выбранная группа — часть адреса главной, как поиск и номер страницы, и проходит через все ссылки списка.
- Тесты Vitest на настоящей PostgreSQL в локальном Docker, в отдельной тестовой базе: рабочие данные тесты не трогают.
- Миграция только добавляет таблицы: ручной откат на предыдущий образ возможен.

**Non-Goals:**

- Тесты интерфейса в браузере (Playwright) и запуск тестов в CI — отдельной работой позже.
- Тесты компонентов React в Vitest: для них нужны новые библиотеки (`@testing-library/react`, jsdom), их владелец не одобрял.
- Изменение тестовых данных (`pnpm db:seed`).

## Decisions

### 1. Две таблицы

- `groups`: `id`, `name` (text, not null), `created_at`. Уникальный индекс по `lower(name)` — две группы, отличающиеся только регистром, база не даст создать даже при одновременной отправке из двух вкладок.
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, оба `ON DELETE CASCADE`; первичный ключ `(contact_id, group_id)` — человек в группе не больше одного раза; индекс `(group_id, contact_id)` для фильтра и чисел на странице «Группы».

Удаление группы или контакта само убирает членство (cascade): отдельного кода и «осиротевших» строк нет.

Альтернативы:

- Массив групп в поле контакта — отвергнуто: переименование и удаление группы пришлось бы переписывать во всех контактах, а уникальность и связи база не проверила бы.
- Хранить в `contact_groups` название группы, а не `id` — отвергнуто по той же причине: переименование.

### 2. Группа в адресе — по номеру: `/?group=12`

Номер не меняется при переименовании, поэтому сохранённая ссылка ведёт в ту же группу (сценарий «Сохранённый адрес группы после переименования»). Разбор — как у номера контакта (`parseContactId`): не число → группы нет. Группа, которой нет в базе, тоже считается «Все» (требование «Ссылка на группу, которой нет»); проверка — один запрос `getGroup(id)` в `React.cache`, общий для ряда меток и списка.

`contactListHref` получает `group`; порядок параметров: `group`, `q`, `page`. Первая страница без группы остаётся просто `/`.

`SearchInput` сейчас при вводе пишет `/?q=…` и теряет остальные параметры — переходит на `contactListHref({ search, group, page: 1 })`, где `group` берётся из текущего адреса. Метки ряда — обычные ссылки `<Link>` с `contactListHref({ search, group, page: 1 })`: выбор группы оставляет поиск.

Альтернатива — название группы в адресе (`?group=Теннис`): читаемо, но ломается после переименования.

### 3. Где лежит код

- `src/db/schema.ts` — две таблицы; миграция `pnpm db:generate --name groups` → `drizzle/0002_groups.sql`.
- `src/lib/groups.ts` (только сервер) — чтение и изменение групп. Каждая функция изменения возвращает результат (`ok` или текст ошибки для человека), без `redirect` и `revalidatePath`, поэтому её легко проверить тестом:
  - `listGroups()` — все группы по алфавиту; `listGroupsWithCounts()` — для страницы «Группы» (`left join` + `count`);
  - `getGroup(id)`, `listContactGroups(contactId)`, `listGroupsOfContacts(contactIds)` — метки для целой страницы списка или «Пора связаться» одним запросом;
  - `createGroup(name)`, `renameGroup(id, name)`, `deleteGroup(id)`, `addContactToGroup(contactId, groupId)`, `addContactToGroupByName(contactId, name)`, `removeContactFromGroup(contactId, groupId)`.
- `src/lib/contacts.ts` — `listContacts` и `countContacts` получают необязательный `groupId`: к условию поиска добавляется `exists (select 1 from contact_groups where contact_id = contacts.id and group_id = …)`. Порядок списка не меняется. Каждый контакт в ответе `listContacts` приходит со своими группами (`groups`), собранными вторым запросом `listGroupsOfContacts` по контактам страницы.
- `src/lib/keep-in-touch.ts` — расчёт срока не меняется; `listOverdueContacts` так же добавляет каждому человеку его группы.
- `src/lib/validation.ts` — `groupNameSchema`: обрезка пробелов, 1–40 символов, тексты ошибок из спеки. Константа `GROUP_NAME_MAX_LENGTH = 40` и типы состояний форм групп — в новом `src/lib/group-form.ts` (общий для браузера и сервера, как `contact-form.ts`).
- `src/lib/format.ts` — `formatContactListSummary` получает признак «выбрана группа» («В группе: N контактов»); `formatGroupSize` («1 контакт», «12 контактов», «пока никого»).
- `src/app/groups/actions.ts` — серверные действия групп: читают форму, зовут `src/lib/groups.ts`, после успеха `revalidatePath("/", "layout")`.
- Страница `src/app/groups/page.tsx` (`/groups`), компоненты в `src/components/`: форма создания, строка группы (переименование и удаление на месте), строка «Группы» в карточке с окошком «+ группа», ряд меток над списком, метки групп в строке.

### 4. Правила названия — в коде и в базе

Пустое и длинное название ловит `groupNameSchema` до запроса. «Уже есть» ловит база:

- создание — `insert … on conflict do nothing returning id`; ничего не вставилось → прочитать существующее название по `lower(name)` и вернуть «Группа «Семья» уже есть» с названием так, как оно записано;
- переименование — `update`; ошибка уникальности `23505` по индексу `lower(name)` → то же сообщение. Переименование «теннис» → «Теннис» индекс не нарушает: это та же строка;
- «+ группа» с названием — в одной транзакции: `insert … on conflict do nothing`, затем найти группу по `lower(name)`, затем `insert into contact_groups … on conflict do nothing`. Так «семья» добавляет в существующую «Семья», а повтор для того, кто уже в группе, ничего не меняет.

Проверка «есть ли такая» отдельным `select` до записи отвергнута: две вкладки могут проскочить её одновременно.

Пропавшие данные: группу или контакт удалили в другой вкладке → `update`/`delete` не нашёл строку или вставка упала с `23503` (внешний ключ) → «Этой группы уже нет. Обновите страницу.» или существующее «Этот контакт не найден…». Убрать из группы того, кого там уже нет, — не ошибка.

Ошибки базы пишутся в лог через `describeDbError`: название группы — данные пользователя, в лог не попадает.

### 5. Алфавит

Везде `order by lower(name), id`. Сравнение по правилам сортировки базы, как и имена на «Пора связаться». Если окажется, что кириллица или «ё» сортируются не по-русски, сравнивать по `translate(lower(name), 'ё', 'е')`, как в поиске.

### 6. Интерфейс

- Ряд меток над списком — серверный компонент внутри `<Suspense>` (запасной вариант — ничего), под строкой поиска, не прилипает к верху вместе с поиском. Метки — ссылки; у выбранной `aria-current="page"` и заливка основным цветом. На телефоне `overflow-x-auto` в одну строку, с `sm` — перенос (`flex-wrap`).
- Метки групп в строке списка, в карточке и на «Пора связаться» — компонент `badge` из shadcn (`pnpm dlx shadcn@latest add badge`), приглушённые цвета (`bg-muted`, `text-muted-foreground`), `text-13`. В строке списка метки и текст «кто это · откуда знакомы» — одна строка с `truncate`, высота строки прежняя `h-16`.
- Окошко «+ группа» — `popover` из shadcn (`pnpm dlx shadcn@latest add popover`) на `@base-ui/react`: Escape, нажатие мимо и возврат фокуса на кнопку уже умеет. Внутри — список групп кнопками (длинный список прокручивается внутри окошка) и форма «Новая группа». На телефоне ширина окошка не больше ширины экрана минус отступы.
- Крестик на метке в карточке — маленькая форма с кнопкой `aria-label="Убрать из группы «Семья»"`, без вопроса.
- Переименование и удаление на странице «Группы» — на месте строки, как удаление контакта (`src/components/delete-contact.tsx`): фокус на безопасную кнопку, Escape отменяет.
- Ссылка «Группы» в шапке главной — между «Пора связаться» и «Добавить контакт», значок `TagsIcon` из lucide-react, оформление как у соседних.
- Цвета, шрифты и отступы — только токены `src/app/globals.css`.
- Если `shadcn add` попытается поставить новый npm-пакет — остановиться и спросить владельца.

Альтернатива для меток в строке списка — третья строка под «кто это»: отвергнута, строки стали бы разной высоты.

### 7. Свежесть данных

Каждое действие с группами после успеха вызывает `revalidatePath("/", "layout")`, как действия с контактами: главная, карточка, «Группы» и «Пора связаться» читаются заново. В карточке после добавления окошко закрывается по успешному ответу действия.

### 8. Тесты: Vitest на настоящей базе

- Vitest — последняя стабильная версия на момент установки (проверить `pnpm view vitest version`), только в `devDependencies`. Команда `pnpm test` → `vitest run`.
- `vitest.config.ts`: среда `node`; псевдоним `@` → `src`; `server-only` подменяется пустым модулем (в Node вне Next.js он бы бросил ошибку); файлы тестов запускаются по одному (`fileParallelism: false`), потому что делят одну базу.
- Тестовая база: глобальная подготовка читает `DATABASE_URL` из `.env` (`process.loadEnvFile`, как `drizzle.config.ts`), создаёт рядом базу с именем `<имя>_test`, если её нет, и применяет к ней миграции из `drizzle/`. Тестам передаётся адрес тестовой базы. Владельцу ничего в `.env` добавлять не нужно.
- Перед каждым тестом таблицы очищаются (`truncate … restart identity cascade`). Защита: очистка отказывается работать, если имя базы не кончается на `_test`.
- Что проверяется. Функции `src/lib/groups.ts`, `src/lib/contacts.ts` и `src/lib/keep-in-touch.ts` — на настоящей базе; разбор адреса, ссылки списка, подписи и правила названия — как обычные функции; серверные действия групп — на настоящей базе, подменяются только `revalidatePath` из Next.js. Проверяем то, что видит человек: какие группы и в каком порядке, кто в списке, какие числа и тексты.
- Сценарии только про вид и поведение в браузере (телефон, окошко, Escape, «Отмена», кнопка «Назад», возврат «Все контакты») Vitest без браузера не проверит. Для них — тесты Playwright, когда подключим e2e; до этого — руками. Список таких сценариев — в `tasks.md`.
- Имена тестов — на английском (правило CLAUDE.md), по одному тесту на сценарий; связь со сценариями — в `tasks.md`.

Альтернативы: подменить базу заглушками — отвергнуто, правило проекта «без моков на настоящей базе»; отдельный контейнер для тестов (testcontainers) — новая библиотека, и Docker-база уже есть.

## Risks / Trade-offs

- [Около трети сценариев до подключения Playwright проверяются только руками] → они перечислены в `tasks.md`; при подключении e2e каждый получает свой тест.
- [`pnpm test` требует запущенной базы в Docker] → понятная ошибка «база не запущена: `docker compose up -d`» из глобальной подготовки; строка в README.
- [Свежая версия Vitest может упереться в правило pnpm «пакет не моложе суток»] → взять предыдущую стабильную, правило не трогать.
- [Сотни людей добавлять в группу по одному через карточку долго] → так решил владелец; массовое добавление — отдельная фича.
- [Ряд меток растёт с числом групп] → на телефоне листается вбок, на компьютере переносится; если групп станут десятки, вернуться к выпадающему списку отдельной правкой.
- [Новый контакт, добавленный при выбранной группе, в неё не попадает] → вне рамок, записано в proposal.

## Migration Plan

1. Миграция `0002_groups`: создать `groups` и `contact_groups` с индексами. Существующие таблицы не меняются, данных не трогает.
2. Выкатка обычная: миграции → новый образ → smoke `/health`.
3. Ручной откат на предыдущий образ возможен без отката миграции: старая версия про новые таблицы не знает и не читает их.
4. После выкатки групп нет ни у кого; главная выглядит как раньше, пока не создана первая группа.
