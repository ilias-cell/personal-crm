# Design

## Context

Зачем и что меняется — в `proposal.md`, поведение и сценарии — в `specs/login`, `specs/data-ownership`, `specs/contact-groups`, `specs/contact-list`, `specs/keep-in-touch`. Исходные требования владельца — `specs/02-пользователи-вход.md`.

Что есть сейчас:

- Входа нет. Прод https://app.therooks.ru открыт всем, кто знает адрес; локально приложение слушает только `127.0.0.1`.
- Таблицы `contacts`, `notes`, `groups`, `contact_groups` в `src/db/schema.ts`, у записей нет владельца. Название группы уникально на всю базу (`groups_name_lower_idx` по `lower(name)`). Последняя миграция — `drizzle/0002_groups.sql`.
- Запросы к базе — в `src/lib/contacts.ts`, `src/lib/groups.ts`, `src/lib/keep-in-touch.ts`. Серверные действия — `src/app/actions.ts`, `src/app/groups/actions.ts`. Карточка (`src/app/contacts/[id]/page.tsx`) вызывает `notFound()`, если контакта нет; страница `src/app/not-found.tsx` — «Здесь ничего нет», вкладка — «Контакт не найден».
- Включены `cacheComponents` и `partialPrefetching`: всё, что читает запрос или базу, должно быть внутри `<Suspense>`. Кеша данных (`use cache`) в проекте нет: каждое открытие читает базу.
- Next.js 16.4: `middleware.ts` теперь называется `proxy.ts` и по умолчанию работает в Node.js. Гайд `node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md`: сессию читать внутри `<Suspense>`, не на верхнем уровне layout; права проверять в каждом серверном действии.
- Миграции применяет `src/db/migrate.ts` (в образе — `tools/migrate.js`, разовый контейнер `migrate` до старта приложения). Тестовые базы `_test` и `_e2e` готовит `src/test/test-database.ts` тем же мигратором Drizzle. Локально `pnpm db:migrate` — это `drizzle-kit migrate`.
- Vitest работает на настоящей базе; подменяются только `revalidatePath` и `redirect`, потому что им нужен запущенный Next.js. e2e (Playwright) собирает приложение и запускает его на порту 3002 с базой `_e2e`; `resetDatabase()` перед каждым тестом очищает все таблицы.
- CI: задания `Checks` (lint, формат, типы, Vitest) и `E2E tests` поднимают Postgres как service. Сборка образа: `pnpm build` с заглушкой `DATABASE_URL`.
- На проде nginx передаёт `X-Forwarded-For $remote_addr`: заголовок перезаписывается и содержит один адрес. Порт приложения 3001 открыт только на `127.0.0.1`.
- Репозиторий на GitHub публичный.

Что проверено по исходникам Better Auth 1.7.18:

- Ссылка хранится в таблице verification. Поле `identifier` — `magic-link:<токен>`. Поле `value` — JSON с почтой в том виде, в каком её прислали.
- Срок ссылки по умолчанию 5 минут. После входа ссылка удаляется, второй раз она не работает.
- Новая ссылка прежние **не отменяет**.
- Неверная, использованная или устаревшая ссылка ведёт на `errorCallbackURL?error=INVALID_TOKEN`.
- Пользователь создаётся при первом переходе по ссылке: `name: ""`, `emailVerified: true`, строки в accounts нет.
- Почту плагин проверяет `z.email()` и в нижний регистр приводит только при поиске и создании пользователя. Пробелы по краям **не убирает**.
- `hooks.before` срабатывает и на HTTP-запрос, и на вызов `auth.api.*`. Он может отклонить запрос через `APIError` или поменять `body`; проверка `body` идёт уже после него.
- Встроенный ограничитель частоты включён, когда `NODE_ENV=production`. Для ссылок входа и перехода по ним это 5 запросов в минуту с одного адреса. Считает он только HTTP-запросы и хранит счётчики в памяти.
- В серверных компонентах (RSC) `nextCookies()` намеренно **не продлевает** вход: продление срабатывает только в route handler'ах и серверных действиях.
- `signOut` закрывает только текущий вход.

## Goals / Non-Goals

**Goals:**

- Каждый запрос к данным идёт с владельцем. Функцию чтения или изменения данных нельзя вызвать без `ownerId`: это ловит проверка типов.
- Все проверки при запросе ссылки — почта, лимиты, отмена прежних ссылок — живут в одном месте. Это место срабатывает и для формы, и для прямого HTTP-запроса к `/api/auth/sign-in/magic-link`.
- Вход продлевается при каждом заходе, и в базе, и в cookie.
- Существующие данные одной миграцией переходят к владельцу. Почта владельца берётся из настройки и в git не попадает. Без этой настройки миграция на непустой базе падает и ничего не меняет.
- Письма во всех окружениях отправляет Nodemailer по одному адресу SMTP из настройки. Сборка одна и та же.
- Тесты без подмены входа: Vitest и e2e проходят настоящий вход через Mailpit.

**Non-Goals:**

- Кеширование данных пользователя (`use cache`, `use cache: private`). Приложение и сейчас читает базу при каждом открытии.
- Возврат после входа на страницу, которую открывали до него: после входа всегда главная (см. Open Questions).
- Защита связи «контакт — группа» на уровне базы составными внешними ключами (см. решение 4).
- Отдельная команда для смены почты владельца после выкатки.

## Decisions

### 1. Better Auth с плагином magicLink и адаптером Drizzle

- Пакет `better-auth` последней стабильной версии на момент установки; по исследованию это 1.7.x. Адаптер Drizzle входит в пакет.
- CLI Better Auth в зависимости не ставим. Таблицы описываем руками в `src/db/schema.ts` по базовой схеме Better Auth, миграцию генерирует наш `drizzle-kit`.
- Конфигурация — `src/lib/auth.ts` (только сервер):
  - `database: drizzleAdapter(db, { provider: "pg", schema, usePlural: true })`;
  - плагин `magicLink({ expiresIn: 15 * 60, storeToken: "hashed", sendMagicLink })`;
  - `session: { expiresIn: 30 дней, updateAge: 1 час }`;
  - `rateLimit: { enabled: false }` (решение 6);
  - `hooks.before` (решение 6);
  - последним плагином — `nextCookies()`.
  - Вход по паролю не включаем: другого способа войти, кроме ссылки, нет.
- Обработчик — `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler(auth)`.
- Настройки: `BETTER_AUTH_SECRET` (не короче 32 символов) и `BETTER_AUTH_URL` (адрес приложения; из него строится ссылка в письме).
- Сборка образа запускается с `NODE_ENV=production`, а Better Auth в проде без секрета падает. Поэтому в `Dockerfile`, рядом с заглушкой `DATABASE_URL`, передаём заглушку `BETTER_AUTH_SECRET` только для шага `pnpm build`. В образ она не попадает.
- `storeToken: "hashed"`: в базе лежит не сама ссылка, а её отпечаток. Утечка копии базы не даёт войти.

Альтернативы:

- Написать вход самим — отвергнуто: Better Auth задан спекой, а сессии, подписанные cookie и одноразовые токены легко сделать неправильно.
- Генерировать схему CLI `auth` — отвергнуто: ещё одна зависимость ради одного раза; таблиц всего четыре, их проще описать руками и проверить тестами.

### 2. Модель данных

Новые таблицы. Имена во множественном числе, колонки snake_case, как у существующих таблиц:

- `users`: `id` text PK, `name` text not null, `email` text not null unique, `email_verified` boolean, `image` text, `created_at`, `updated_at`. Почта всегда хранится без пробелов и в нижнем регистре.
- `sessions`: `id`, `token` unique, `user_id` → `users.id` ON DELETE CASCADE, `expires_at`, `ip_address`, `user_agent`, `created_at`, `updated_at`; индекс по `user_id`.
- `accounts`: базовая таблица Better Auth. Для входа по ссылке она пустая, но адаптер ожидает модель.
- `verifications`: `id`, `identifier`, `value`, `expires_at`, `created_at`, `updated_at`; индекс по `identifier`.
- `login_emails` — отправленные письма входа, для лимитов:
  - колонки `id`, `email`, `ip` (text, null — адрес неизвестен), `created_at`;
  - индексы `(email, created_at)` и `(ip, created_at)`;
  - строки старше часа удаляются при каждой новой записи.

Изменения в существующих таблицах:

- `contacts.owner_id` text not null → `users.id`, без каскада: удаления аккаунта нет, а случайно стереть данные база не даст.
  - Индекс `contacts_created_at_idx` заменяется на `(owner_id, created_at desc, id desc)`: это порядок главной внутри одного владельца.
- `groups.owner_id` text not null → `users.id`.
  - Уникальный индекс `groups_name_lower_idx` заменяется на `(owner_id, lower(name))`: у каждого свои «Друзья».
- `notes` и `contact_groups` не меняются: заметка принадлежит владельцу контакта, членство — владельцу контакта и группы.

Альтернатива — `owner_id` и в `notes`: отвергнуто. Это дублирование, которое может разойтись с владельцем контакта, а спека прямо говорит, что заметки принадлежат владельцу контакта.

### 3. Миграция `0003_login` и почта владельца

`pnpm db:generate --name login` создаёт таблицы и колонки. Переход данных дописываем в тот же файл руками. Порядок в файле:

1. Создать `users`, `sessions`, `accounts`, `verifications`, `login_emails`.
2. Блок `DO`: если в `contacts` или `groups` есть строки, а `current_setting('crm.owner_email', true)` пустая, выполнить `RAISE EXCEPTION` с текстом «OWNER_EMAIL is not set: existing contacts and groups need an owner».
3. Если данные есть, создать владельца:
   - `id` — `gen_random_uuid()::text`;
   - `email` — `lower(btrim(setting))`;
   - `name` — `''`;
   - `email_verified` — `true`, чтобы Better Auth при первом входе не закрыл его входы как «неподтверждённого».
4. Добавить `owner_id` с разрешённым NULL и заполнить его id владельца. Затем `SET NOT NULL`, внешний ключ, новые индексы, удаление старых.

Как настройка попадает в SQL:

- Общий модуль `src/db/run-migrations.ts`:
  - открывает **одно** соединение (`pg.Client`);
  - выполняет `select set_config('crm.owner_email', $1, false)` со значением `OWNER_EMAIL`;
  - запускает мигратор Drizzle на этом же соединении.
- Мигратор Drizzle применяет все новые миграции в одной транзакции. Если миграция упала, база остаётся как была.
- Модулем пользуются:
  - `src/db/migrate.ts` (образ, прод);
  - `src/test/test-database.ts` (базы `_test` и `_e2e`; они пустые, и настройка им не нужна);
  - локальная команда `pnpm db:migrate`. Она переходит с `drizzle-kit migrate` на `tsx --env-file=.env src/db/migrate.ts`, иначе локальная база с данными не получит владельца.
- `drizzle-kit migrate` на непустой базе упадёт с понятной ошибкой из шага 2.
- Почта владельца в лог не пишется. Миграция пишет только сам факт, что владелец создан, и число переданных записей.

Альтернативы:

- Почта в коде миграции — отвергнуто владельцем: репозиторий публичный.
- Отдать данные первому, кто войдёт, — отвергнуто: если первым войдёт друг, ему достанется всё.
- `owner_id` с NULL и «дозаполнение» при входе владельца — отвергнуто: NULL-владелец во всех запросах и вечная ветка кода ради одного раза.

### 4. Доступ к данным: владелец — обязательный параметр

- `src/lib/session.ts` (только сервер):
  - `getCurrentUser()` в `React.cache`: `auth.api.getSession({ headers: await headers() })` → `{ id, email } | null`;
  - `requireUser()`: нет входа → `redirect("/login")`.
- Все функции `src/lib/contacts.ts`, `groups.ts`, `keep-in-touch.ts` получают первым параметром `ownerId: string`, и каждый запрос фильтрует по нему:
  - контакты и группы — по `owner_id`;
  - заметки и членство — через контакт и группу этого владельца.
- Страницы вызывают `requireUser()` внутри уже существующих `<Suspense>` и передают `user.id` дальше. Каждое серверное действие первым делом вызывает `requireUser()`; номер записи из формы или адреса никогда не используется без владельца.
- Чужой контакт неотличим от несуществующего: `getContact(ownerId, id)` вернёт `null`, а дальше сработает тот же `notFound()`. Сообщения в действиях — прежние `CONTACT_NOT_FOUND_MESSAGE` и `GROUP_NOT_FOUND_MESSAGE`.
- Связь «контакт — группа»:
  - `addContactToGroup` вставляет членство через `insert … select`, только если контакт и группа принадлежат владельцу. 0 строк — то же сообщение «контакта или группы нет».
  - `addContactToGroupByName` в одной транзакции сначала проверяет, что контакт свой (иначе группа не создаётся), затем создаёт или находит группу **этого владельца**.
  - `removeContactFromGroup` удаляет членство, только если и контакт, и группа свои.
- Чужая группа в адресе главной: `getGroup(ownerId, id)` вернёт `null` — то же поведение, что у удалённой группы.

Альтернативы:

- Row Level Security в PostgreSQL — отвергнуто: роль приложения и установка пользователя на каждое соединение из общего пула сложнее и непривычнее, чем параметр в каждой функции. Тесты на каждую функцию ловят пропуск фильтра.
- Составные внешние ключи `(contact_id, owner_id)` в `contact_groups` — отвергнуто: заметно усложняет миграцию. Проверка в двух функциях закрыта тестами.

### 5. Закрытие страниц: `proxy.ts` и проверка в данных

- `src/proxy.ts` — быстрая проверка без базы. На каждый запрос страницы смотрит, есть ли cookie входа (`getSessionCookie` из Better Auth); нет — redirect на `/login`.
- Исключения matcher:
  - `/login` и всё под ним;
  - `/api/auth/*`;
  - `/health`;
  - `/_next/static`, `/_next/image`, `icon.svg`.
- Настоящая проверка — `requireUser()` в данных и действиях (решение 4). Cookie есть, но вход истёк или закрыт — данные не отдаются, страница уходит на `/login`. Next.js и Better Auth прямо говорят, что proxy не должен быть единственной защитой: серверные действия идут POST-запросом на маршрут страницы.
- `/login`: уже вошедшего отправляет на `/`.

Альтернатива — полная проверка сессии с запросом к базе в `proxy.ts`: отвергнуто. Запрос к базе на каждую предзагрузку ссылок, а продление cookie из proxy не проверено. Цена отказа: на просроченном входе на долю секунды может мелькнуть пустая статичная оболочка страницы без данных до перехода на вход.

### 6. Запрос ссылки: серверное действие и hook Better Auth

Форма входа `src/components/login-form.tsx` (`useActionState`, как формы контакта) отправляет серверное действие `requestLoginLink` из `src/app/login/actions.ts`. Действие:

- вызывает `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers: await headers() })`;
- переводит ответ в состояние формы:
  - успех → «Ссылка для входа отправлена на <почта>»;
  - `INVALID_EMAIL` → ошибка под полем;
  - `TOO_MANY_LOGIN_EMAILS` → «Слишком часто, попробуйте через несколько минут».

Все проверки — в `hooks.before` для `ctx.path === "/sign-in/magic-link"`, по порядку:

1. **Почта.** `loginEmailSchema` в `src/lib/validation.ts`: trim → нижний регистр → не длиннее `EMAIL_MAX_LENGTH` → `z.email()`. Это то же правило, что у почты контакта.
   - Ошибка → `APIError("BAD_REQUEST", { code: "INVALID_EMAIL", message: "Проверьте адрес почты" })`.
   - Успех → `body.email` заменяется приведённой почтой.
   - Пустое поле — та же ошибка.
2. **Лимиты.** `reserveLoginEmail(email, ip)` в `src/lib/login-limits.ts`, одна транзакция:
   - `pg_advisory_xact_lock` по почте и по адресу, чтобы две одновременные отправки не прошли обе;
   - счёт по `login_emails` — по почте за 10 минут (не больше 3) и по адресу за час (не больше 10);
   - если лимит не превышен — запись строки.
   - Превышен → `APIError("TOO_MANY_REQUESTS", { code: "TOO_MANY_LOGIN_EMAILS", message: "Слишком часто, попробуйте через несколько минут" })`.
   - Адрес — первое значение `x-forwarded-for`, его ставит nginx. Нет заголовка (локально, в тестах) — `NULL`, и все такие запросы делят один счётчик.
   - Неверная почта сюда не доходит и лимит не тратит.
3. **Прежние ссылки.** `revokeLoginLinks(email)` удаляет из `verifications` строки, у которых `identifier like 'magic-link:%'` и `value::jsonb->>'email' = email`. Новая строка создаётся плагином уже после hook'а, поэтому её это не задевает. При сработавшем лимите прежние ссылки остаются рабочими.

Hook стоит раньше записи ссылки и раньше отправки, поэтому:

- прямой HTTP-запрос в обход формы проходит те же проверки;
- письмо не уходит, если проверка не прошла.

Письмо считается отправленным в момент записи. Если SMTP упал после записи, попытка всё равно израсходована: так лимит строже, не слабее.

Встроенный ограничитель Better Auth выключаем:

- для переходов по ссылкам он дал бы 5 в минуту с одного адреса — e2e на одной машине упёрлись бы в него;
- счётчики он держит в памяти и обнуляет при перезапуске;
- лимиты из спеки он не заменяет.

Перебрать ссылку невозможно: токен из 32 случайных символов живёт 15 минут.

Альтернативы:

- Проверки только в серверном действии — отвергнуто: прямой POST на `/api/auth/sign-in/magic-link` их обходит, а спека требует проверки и для запросов не из формы.
- Проверки в `sendMagicLink` — отвергнуто: к этому моменту плагин уже записал ссылку, а отменить прежние ссылки, не задев новую, можно только зная внутренний формат токена.
- Форма через клиент Better Auth в браузере — отвергнуто: лишний клиентский код, а ошибки под полем удобнее отдавать так же, как в остальных формах.

### 7. Ссылка, страница «Ссылка устарела» и выход

- Срок ссылки — `expiresIn: 900` секунд. Одноразовость и проверку срока делает плагин.
- Неудачный переход (`INVALID_TOKEN` или любая другая ошибка проверки) ведёт на `src/app/login/expired/page.tsx`. На странице «Ссылка устарела, запросите новую» и кнопка «Запросить новую ссылку» → `/login`. Оформление — компонент `Empty`, как у пустых состояний приложения.
- Удачный переход: Better Auth ставит cookie и ведёт на `/`.
- Выход: форма с серверным действием `signOut` → `auth.api.signOut({ headers })` → `redirect("/login")`. Удаляется только текущая сессия; `nextCookies()` стирает cookie.

### 8. Продление входа: 30 дней с последнего захода

- `session.expiresIn = 30 дней`, `updateAge = 1 час`. Вход продлевается до «сейчас + 30 дней», если с прошлого продления прошёл хотя бы час. Расхождение с «ровно 30 дней от последнего захода» — не больше часа; записей в базу — не чаще раза в час на устройство.
- В серверных компонентах Better Auth не продлевает. Поэтому клиентский компонент `src/components/session-keep-alive.tsx` в шапке (только у вошедшего) при открытии приложения и при каждой смене страницы делает `fetch("/api/auth/get-session")`. Это route handler: там Better Auth продлевает и запись в базе, и cookie. Клиентская библиотека Better Auth не нужна.
- Серверные действия тоже продлевают вход: `requireUser()` там идёт через `getSession` в контексте действия.
- Cookie без cache (`cookieCache` не включаем): выход и истечение срока действуют сразу.

Альтернатива — продлевать в `proxy.ts`. Отвергнуто: в Better Auth это не описано и не проверено, а при переходах между страницами внутри приложения запросы приходят с заголовком `RSC`, и `nextCookies()` продление пропускает.

### 9. Письма: Nodemailer по адресу SMTP из настройки

- `src/lib/mailer.ts`: `nodemailer.createTransport(process.env.SMTP_URL)`, транспорт создаётся один раз. Значения по окружениям:
  - у владельца на компьютере и в тестах — `smtp://127.0.0.1:1025` (Mailpit);
  - на сервере — `smtps://resend:<ключ>@smtp.resend.com:465`. Ключ Resend состоит из букв, цифр и `_`, поэтому кодировать его в адресе не нужно.
- Отправитель — настройка `MAIL_FROM`, на сервере `Личная CRM <noreply@mail.therooks.ru>`.
- Пакет `nodemailer` последней стабильной версии. С 10-й версии он на TypeScript и несёт свои типы, `@types/nodemailer` не нужен; проверить при установке. Правило pnpm «пакет не моложе суток» может выбрать предыдущую версию — это нормально.
- Содержание письма — чистая функция `buildLoginEmail(url)` в `src/lib/login-email.ts` → `{ subject, html, text }`:
  - тема «Вход в Личную CRM»;
  - кнопка-ссылка «Войти» в HTML и сама ссылка в тексте;
  - «Ссылка работает 15 минут.»;
  - «Если вы не запрашивали вход — просто проигнорируйте письмо».
  - HTML — простая таблица со встроенными стилями (почтовые программы не читают CSS-файлы). Цвета берутся из значений дизайн-токенов `globals.css`, скопированных в модуль письма: в письме CSS-переменные не работают.
- Сбой SMTP пишется в лог без почты получателя и без ссылки: в проекте данные людей в лог не попадают. Пользователь видит общую ошибку «Не удалось отправить письмо. Попробуйте ещё раз.».

Альтернатива — HTTP API Resend через его SDK: отвергнуто. Спека требует Nodemailer для всех окружений, а SMTP Resend это позволяет.

## Risks / Trade-offs

- [Почтовые программы и антивирусы иногда сами открывают ссылки из писем для проверки и тем самым «используют» одноразовую ссылку] → Пользователь увидит «Ссылка устарела». Проверяем руками на настоящем ящике владельца после выкатки. Если повторится — отдельной правкой добавить промежуточную страницу с кнопкой «Войти»; это меняет спеку, поэтому только с согласия владельца.
- [Опечатка в `OWNER_EMAIL` на сервере: данные уйдут пользователю, под которым никто не войдёт, и владелец увидит пустой список] → Перед merge владелец сверяет строку; после выкатки — проверка руками «вижу свои контакты». Исправление — откат (ниже) или разовая правка почты пользователя в базе, только с согласия владельца.
- [Старая версия приложения не работает с новой базой: `owner_id NOT NULL`] → Откат только вместе: база из бэкапа выкатки и прошлый образ (Migration Plan).
- [Отмена прежних ссылок опирается на формат строки ссылки в Better Auth: `magic-link:` и `email` в JSON] → Тест «новая ссылка отменяет старую» идёт через настоящий плагин и упадёт при обновлении Better Auth, если формат поменяется.
- [Без заголовка `x-forwarded-for` (локально, в тестах) все запросы делят один счётчик адреса] → На сервере заголовок ставит nginx; локально 10 писем в час хватает с запасом, e2e очищают счётчики перед каждым тестом.
- [Общий дневной лимит Resend на бесплатном тарифе (по данным поиска — 100 писем в день; не проверено на сайте Resend) всё равно можно выбрать с многих адресов] → Лимиты по почте и по адресу сильно сужают это. Если упрёмся — тариф или общий дневной лимит отдельной правкой с согласия владельца.
- [У вошедшего с просроченной cookie на долю секунды мелькнёт статичная оболочка страницы без данных] → Данных в ней нет; дальше переход на вход.
- [Вход продлевается только из браузера с JavaScript (`SessionKeepAlive`) и из серверных действий] → Приложение и так требует JavaScript для форм; без продления вход просто кончится через 30 дней после последнего продления.
- [Better Auth отдаёт эндпоинты, которые нам не нужны, например смену имени через `/api/auth/update-user`] → Имя нигде не показывается и ни на что не влияет. Входа по паролю, смены почты и удаления аккаунта нет: они выключены по умолчанию.
- [Письма с нового домена могут попадать в спам первые дни] → Отправка с отдельного поддомена `mail.therooks.ru`, а не с основного `therooks.ru` (так советует Resend). Записи SPF и DKIM добавляет владелец до выкатки; проверка руками по настоящему письму.
- [Свежая версия Nodemailer может не пройти правило pnpm «не моложе суток»] → pnpm сам возьмёт предыдущую версию; правило не трогаем.

## Migration Plan

Реализация не ждёт почтового домена. Всё до выкатки — разработка, Vitest, e2e, CI — работает с Mailpit, без DNS. Решение владельца от 2026-11-08: записей DNS для `mail.therooks.ru` пока нет, поэтому PR открывается без автовлития и ждёт, пока не будут выполнены шаги 1–2 ниже. До этого прод остаётся как сейчас: без входа.

До merge (делает владелец, агент подсказывает команды):

1. Resend:
   - аккаунт;
   - домен `mail.therooks.ru`;
   - записи DNS, которые покажет Resend (только человек), и дождаться статуса «Verified»;
   - ключ API с правом только отправки и только для этого домена.
2. На сервере в `~/crm/.env` добавить строки `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=https://app.therooks.ru`, `SMTP_URL`, `MAIL_FROM`.
   - Секрет генерируется на сервере командой, не выводясь на экран.
   - Ключ Resend вводится через `read -s`: так он не попадёт в историю команд и в вывод.
   - Права файла остаются 600.
3. Агент показывает владельцу миграцию `0003_login.sql` — она меняет существующие данные; правило CLAUDE.md.
4. Локально до merge: `pnpm db:migrate` на своей базе с данными, вход под своей почтой, контакты на месте.

Выкатка (как обычно, после merge):

- `deploy.sh` проверяет строки `.env` → бэкап базы → миграции (владелец получает данные) → новое приложение → smoke `/health`.
- Если какой-то строки нет, выкатка останавливается до бэкапа. Если упала миграция, новая версия не стартует, прежняя работает.

После выкатки, проверка руками:

- `/health` отвечает новой версией;
- без входа открывается страница входа;
- письмо приходит на настоящий ящик владельца, ссылка впускает;
- число контактов, заметок и групп совпадает с прежним;
- друг или вторая почта видит пустой список.

Откат (только вручную, запускает владелец). Только вместе — база из бэкапа выкатки и прошлый образ:

1. `ssh crm '~/crm/deploy.sh "$(cat ~/crm/state/previous)"'` — прошлый образ. Новых миграций для него нет, он стартует на новой схеме: контакты открываются, добавить новые нельзя — ожидаемо до шага 2.
2. `ssh -t crm '~/crm/restore.sh ~/crm/backups/deploy-….dump'` — бэкап, снятый этой выкаткой. Скрипт загрузит старую базу и поднимет то приложение, которое работает сейчас, то есть прошлое.
3. Всё, что внесли в приложение после выкатки (контакты друзей, новые заметки), пропадёт из рабочей базы и останется только в копии `before-restore`.

Порядок «сначала образ, потом база» выбран потому, что `restore.sh` после загрузки бэкапа применяет миграции **работающей** версии (шаг «Migrations of the running app version»). При обратном порядке (сначала база) работает ещё новый образ, и миграция входа тут же вернёт базе новую схему. (Первоначально здесь стоял обратный порядок; исправлено при реализации, когда читался `restore.sh`.) README получает этот раздел.
